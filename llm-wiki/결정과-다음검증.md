## 검토했지만 도입을 뜻하지 않는 것

- **PostgreSQL·pgvector:** 검토 질문이 있었으나 현재 저장소의 운영 경로는 SQLite·FAISS입니다. 실제 동시 쓰기·복구·권한·규모 요구가 기존 구성의 한계를 입증하면 비교할 과제입니다.
- **영어 번역문도 별도 벡터화:** 현재 영어는 키워드 보조입니다. 별도 벡터가 정확도·시간·저장량에 주는 영향은 같은 질문으로 비교해야 합니다.
- **3그램 또는 검색 전체 교체:** 현재 2그램 보조를 대체해야 한다는 검증 결과가 없습니다. 숫자·코드·짧은 한국어 표현의 누락을 함께 비교해야 합니다.
- **LEV·CLM·GLiNER·Laya 자동 채택:** 완료된 실험의 한계 때문에 운영 연결은 보류입니다. Core ML 직접 실행과 Ollaya의 CPU 실행을 같은 성공으로 간주하지 않습니다.
- **모델 학습:** 사용자가 가능성을 검토했으나 현재 프로그램의 학습 단계는 없습니다. 학습용·개발용·독립 평가 자료를 먼저 구분해야 합니다.

## LLM Wiki를 업무 검색에 활용하는 제안

상태: **제안·미구현·효과 미측정**. 이번에 요청한 개발 지식 위키 작성과 구분합니다.

‘스핀 진동’처럼 설비·증상별로 사례를 묶어 발생 조건, 기록된 원인, 조치, 실제 결과와 한계를 요약하는 방식입니다. 각 사실에 CS 번호·날짜·원문 셀을 연결하고 서로 다른 장비 조건이나 상충하는 결과를 뭉개지 않아야 합니다. 원문이 갱신되면 영향을 받은 요약을 다시 검토해야 합니다.

제안한 최소 비교는 주제 10개에서 기존 검색·답변과 요약을 보조로 추가한 방식을 같은 질문으로 대조하는 것입니다. 조치 적합성·인용 정확성·잘못된 성공 판단·답변 가능 사례의 누락·응답 시간을 함께 봅니다. 작성한 요약을 정답 자료로 삼아 스스로 채점하지 않습니다.

이 구상은 [Karpathy의 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)를 현재 업무에 적용한 제안입니다. 원문이 제안한 개인 지식 관리 방식 자체가 10만 건 CS 자료의 성능을 입증하는 것은 아닙니다.

## 다음 판단에 필요한 확인

1. 실제 Windows GPT OSS 120B와 허가된 DRM 파일에서 등록·검토·검색·후속 질문을 확인합니다. 로컬 모의 검사 통과와 분리해 기록합니다.
2. 현업 담당자가 판정한 새로운 질문·원문 묶음으로 조치·결과·날짜·필수 근거 열을 검토합니다. 이미 본 합성 질문의 반복 성공으로 대체하지 않습니다.
3. 서버 적재 문맥·추론 출력·참고 사례 수·대기 시간을 함께 측정하여 긴 질문의 실패 원인을 구분합니다.
4. 위키 요약 실험을 시작한다면 먼저 질문과 판단 기준을 고정하고 운영 DB와 분리합니다. 효과가 확인된 뒤 제품 연결 범위를 결정합니다.

이 목록은 후속 작업 제안이며 이번 문서 작성으로 자동 실행하거나 외부 업무 자료를 요청한 것은 아닙니다. 실제 진행 시 승인된 범위·자료·환경을 기준으로 기록을 추가합니다.
