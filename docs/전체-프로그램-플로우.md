# 전체 프로그램 플로우

운영 흐름 기준: 2026-09-26. 검토 저장 구조 정리와 별도 GLiNER·LEV 실험, CLM 장치 검사 실패를 반영했습니다. 웹 UI를 중심으로 그렸으며, CLI도 같은 입력·다듬기·검토·검색 함수를 사용합니다. 화살표는 처리 순서 또는 데이터 전달을 뜻하고, 점선은 선택 기능이나 보조 경로입니다. 모델을 학습시키는 단계는 없습니다. 비개발자용 설명은 [임원 보고서](임원보고서.md)에서 확인할 수 있습니다.

## 1. 전체 흐름

```mermaid
flowchart TD
    START([프로그램 실행]) --> SETTINGS[설정·지원 양식·기존 DB 읽기]
    SETTINGS --> UI[웹 UI 또는 CLI]
    SETTINGS -. 임베딩 설정이 있으면 .-> BOOT[모델 연결 확인·기존 벡터 준비]

    UI --> INPUT{입력 파일}
    UI --> QUEUE[여러 파일 경로를 대기열에 등록<br/>최대 100파일 순차 처리]
    QUEUE --> INPUT
    INPUT -->|일반 Excel| XLS[openpyxl로 읽기<br/>CSList 128열 또는 누적 CS 28열]
    INPUT -->|DRM Excel| DRM[Excel 앱과 xlwings로 읽기<br/>수식은 계산 완료 값을 사용]
    INPUT -->|변환 파일| CACHE[rag.jsonl.gz 읽기]
    XLS --> CHECK[열 이름·접수번호·원문 검사]
    DRM --> CHECK
    CACHE --> CHECK
    CHECK -->|열 이름 불일치| MAP[열 대응 수정 후 다시 검사]
    MAP --> CHECK
    CHECK -. 선택: 한 번 변환 .-> EXPORT[원문·셀 위치를 변환 파일에 보관]
    EXPORT --> CACHE

    CHECK -->|검사 통과| IMPORT[DB에 추가·갱신<br/>접수번호별 원문 누적 등록]
    IMPORT --> CONFLICT{같은 양식 내 다른 파일의 동일 번호와 내용 충돌?}
    CONFLICT -->|예| STOP[해당 파일 등록 중단 · 기존 DB 보존]
    STOP -. 대기열이면 다음 파일 .-> QUEUE
    CONFLICT -->|아니요| DOC[(SQLite 원문 보관<br/>양식별 문서를 같은 CS 번호로 조회)]
    DOC --> NORMAL[DB 원문으로 LLM 한국어 다듬기<br/>누적 자료는 중국어·영어 번역 후 검사·보정]
    NORMAL --> READY{전체 행 준비 완료?}
    READY -->|아니요| KEEP[성공분 체크포인트 보관<br/>기존 검색 자료 유지]
    KEEP -. 이어서 실행 .-> NORMAL
    READY -->|예| SAVE[수정 제안 확정 · 원문은 별도 보존]
    SAVE -. 검토 .-> REVIEW[개별·일괄 채택 / 직접 수정 / 원문 유지]
    REVIEW --> EFFECTIVE[검토한 접수만 저장 · 검색용 유효 문장 갱신]

    DOC --> KO[한국어 키워드 색인<br/>단어·증상·한글 2그램 보완]
    EFFECTIVE --> KO
    EFFECTIVE --> EMB
    EFFECTIVE -. 선택 .-> EN
    DOC -. 영어 변환 실행 또는 검토 후 자동 갱신 .-> EN[현재 유효 문장을 영어로 번역<br/>실패 셀 최대 3회 보완]
    EN --> ENIDX[영어 번역 저장·영어 키워드 색인]
    DOC -. 임베딩 설정에 따라 .-> EMB[주요 증상 필드 임베딩<br/>원문과 채택문 사용]
    EMB --> VEC[SQLite 벡터 저장·FAISS 색인]

    UI --> Q[한국어 문제 현상 질문]
    Q --> QC{건수 집계 질문?}
    QC -->|예| COUNT[DB에서 CS 번호 중복을 제외하고 집계]
    COUNT --> RESULT[결과·근거를 화면에 표시]
    QC -->|아니요| SEARCH[설정에 따라 키워드·벡터·결합 검색<br/>접수번호·코드·날짜는 정확 검색]
    KO --> SEARCH
    ENIDX -. 영어 검색 사용 시 .-> SEARCH
    VEC --> SEARCH
    SEARCH --> FOUND{관련 후보가 있는가?}
    FOUND -->|아니요| EMPTY[관련 기록 없음 안내]
    EMPTY --> RESULT
    FOUND -->|예| ANSWER[LLM 한국어 답변 생성<br/>원문 근거 검사·필요 시 1회 재요청]
    ANSWER --> RESULT
    UI -. 진단 .-> TRACE[LLM 요청·응답 / 진행 상황 / 검색 비교]
```

**입력 검사·파일 변환과 DB 등록은 다른 단계입니다.** DB 등록 완료 후에는 Excel 없이 다듬기·검토·번역·벡터·질문을 처리합니다. 원문 등록만으로 단어 검색이 가능하고, 임베딩 자동 갱신이 켜져 있으면 원문 기반 벡터도 준비합니다. 같은 내용은 재사용하며, 같은 원본에서 변경된 접수만 갱신하고 이번 파일에 없는 기존 접수는 유지합니다.

일반 다듬기에서는 제안을 바로 채택하지 않습니다. 검토에서 채택·직접 편집한 값이 있으면 그 값을 사용하고, 없으면 원문을 사용합니다. 미채택 제안은 영어 번역과 벡터 입력에 넣지 않습니다. 야간 자동 처리에서는 검사 통과 미검토 제안을 자동 채택합니다.

새 누적 양식은 `19~26년 누적_2600831` 시트의 28열을 그대로 보관합니다. `CS NO`와 기존 `CS 접수번호`는 같은 업무 번호이며, 서로 다른 양식의 문서는 덮어쓰지 않고 함께 조회합니다. 자료 목록은 원문 문서 수, 전체 접수 집계는 중복을 제외한 CS 번호 수입니다.

누적 자료의 한국어 번역은 문장 다듬기의 수정 제안으로 생성합니다. 검토 채택 후 단어 검색과 벡터에 반영되며, 인용에는 원래 언어의 원문과 셀 위치를 사용합니다. 식별자·날짜·빈칸을 보존하고 `2小时`처럼 숫자에 붙은 단위는 원문 표기를 유지합니다.

영어 번역 결과는 영어 **키워드 검색**에 사용합니다. 현재 영어 번역문을 별도로 임베딩하는 경로는 없습니다. 기존 벡터 입력 필드는 제목·문제현상·현상·제품군·UNIT명·알람코드이며, 누적 자료는 Defect 유형·상세, 설비·설비군 간소화, 기인 모듈·부품도 포함합니다. 신규 파생 검색 규칙은 기존 DB의 첫 색인 확인 때 한 번 갱신하며 원문과 검토를 보존합니다.

### 입력 오류와 수식 처리

Excel 연결 방식은 계산 완료 상태를 확인하고 수식의 결과값을 읽습니다. 계산 중·대기는 F9 계산 후 재실행하도록 안내하며 실제 오류 값은 셀 주소와 함께 거절합니다. 수식 자체를 실행하거나 원본 파일을 변경하지 않습니다. 일반 파일 읽기는 수식을 계산하지 않고 Excel 연결 방식을 안내합니다.

열 검사에서는 제목과 값이 모두 빈 뒤쪽 열만 제외합니다. 중간 빈 제목·중복·예약 이름·이름 없는 데이터 열은 파일·시트·셀 위치와 수정 방법을 표시합니다. 뒤쪽 행에서 무제목 열의 값이 발견돼도 전체 입력을 실패 처리하고 기존 DB·변환 파일을 보존합니다. UI는 오류가 난 입력 영역을 펼치고 알림으로 이동합니다.

### 여러 파일 등록 대기열

```mermaid
flowchart TD
    A[경로를 한 줄에 하나씩 입력<br/>읽기 방식 선택] --> B[대기열 등록 시작]
    B --> C{다음 파일이 있는가?}
    C -->|예| D{이미 처리한 경로인가?}
    D -->|예| SKIP[경로 중복 제외 표시]
    SKIP --> C
    D -->|아니요| E[파일 읽기와 열·접수번호 검사]
    E --> F{다른 원본과 내용 충돌 없이 저장 가능한가?}
    E -->|읽기·양식 오류| ERR[그 파일 실패 기록<br/>앞선 성공 파일 보존]
    F -->|아니요| ERR
    F -->|예| SAVE[파일 단위 DB 저장<br/>신규 추가·동일 재사용·같은 원본 수정 갱신]
    SAVE --> C
    ERR --> C
    C -->|아니요| V[등록 성공 파일이 있고 자동 갱신을 켰다면<br/>필요한 벡터를 한 번 갱신]
    V --> R[파일별 결과 확인]
    R -. 입력 오류 수정 후 실패 파일만 재시도 .-> B
    R --> NEXT[DB 문장 다듬기 또는 야간 자동 실행]
```

브라우저는 목록을 서버에 한 번 전달하고 진행 상황을 조회합니다. 파일을 하나씩 읽고 저장하므로 여러 Excel 전체를 동시에 메모리에 올리지 않습니다. 작업 중 새 목록을 시작하지 못하게 기존 공유 작업 잠금을 사용합니다. 브라우저 새로고침·종료와 관계없이 서버는 계속 처리하지만, 서버 재시작 후 대기 목록 복구는 지원하지 않습니다. 재등록 시 저장된 동일 원문은 재사용합니다.

## 2. 문장 다듬기와 검토

```mermaid
flowchart TD
    A[DB 원문과 기존 처리 결과 확인<br/>Excel 재연결 없음] --> B{같은 원문·설정의 성공 결과가 있는가?}
    B -->|예| C[성공 결과 재사용]
    B -->|아니요| D[접수·작업 그룹별 수정 대상 셀 선택]
    D --> E[LLM 한국어 다듬기]
    E --> F{응답 검사 통과?}
    F -->|예| G[성공 제안을 체크포인트에 저장]
    F -->|정상 종료했지만 내용 검사 실패| H[오류 사유를 넣어 1회 보정<br/>숫자 오류 셀은 숫자·단위·코드 보호]
    F -->|통신 오류·잘림 등| J[실패 기록·다음 행 계속]
    H --> I{보정 결과}
    I -->|검사 통과| G
    I -->|숫자 보호·보존 오류만 남음| K[해당 셀은 원문으로 복귀<br/>복귀 사유 보관]
    I -->|기타 오류| J
    K --> G
    C --> L{전체 행 준비 완료?}
    G --> L
    J --> L
    L -->|아니요: 실패 행 존재| M[기존 검색 자료 유지<br/>이어서 실행하면 성공분 재사용]
    M -. 사용자 재실행 .-> A
    L -->|예| N[원문·제안·접수 문서·검색 색인 갱신]
    N --> O[사용자 검토: 개별 또는 일괄 반영]
    O --> P[원문·숫자·단위·검토 대상 재검사]
    P -->|통과| R[검토한 접수만 저장·유효 문장 결정<br/>해당 접수 색인 갱신·오래된 파생 자료 제외]
    P -->|실패| O
    R -->|저장 실패·함께 롤백| O
    R -->|저장 완료| S[설정에 따라 필요한 벡터 먼저 갱신]
    S --> T[설정에 따라 해당 접수 영어 자동 갱신]
```

- 문장 다듬기와 영어 번역의 동시 처리 설정은 기본 200, 최대 1,000입니다. 서버에서 실제로 동시에 계산하는 수와는 다릅니다.
- 문장 다듬기는 완료한 성공분을 체크포인트에 저장합니다. 실패가 남으면 새 검색 자료 전체를 확정하지 않습니다.
- 검토 저장은 원문 등록에서 쓰던 변경분 색인 갱신을 재사용합니다. 최신 색인에서는 검토한 접수만 읽고 다시 만들며, 모든 접수를 검토할 때는 기존 전체 갱신 방식을 사용합니다. 구형 색인은 한 번 전체 이관하며 이관이 저장 트랜잭션을 먼저 확정하지 않습니다. 빈 검토는 생략하고, 전체 HTML 보고서 조회는 저장과 분리합니다.
- 일괄 채택은 원문·제안을 순서대로 읽어 검사하며, 제안 JSON이 손상된 접수도 실패 목록으로 남깁니다. 정상 제안과 기존 검토는 보존합니다. 같은 원문의 중복 읽기와 원문 등록에 불필요한 LLM 다듬기 지문 계산은 제거했습니다.
- 다듬기 직후에는 벡터를 생성하지 않습니다. 검토 저장 후 벡터를 먼저 갱신하고 영어 번역을 실행하며, 어느 쪽이 실패해도 검토 저장을 취소하지 않습니다. 시작 시 준비·파일 변환 후 준비·수동 벡터 생성은 유지합니다.

## 3. 영어 번역과 자동 보완 3회

```mermaid
flowchart TD
    A[처리 대상 접수 선택] --> B[제목과 수정 대상 열의 유효 값 선택<br/>채택·직접 편집 값 우선, 없으면 원문]
    B --> C{번역할 텍스트가 있는가?}
    C -->|아니요| NEXT[다음 접수]
    C -->|예| D{같은 내용·설정의 정상 번역이 있는가?}
    D -->|예| SAVE[번역 재사용·실패 기록 삭제]
    D -->|아니요| SIZE{입력 길이가 제한 이내인가?}
    SIZE -->|아니요| SPLIT[셀별 또는 안전한 공백 경계로 분할]
    SPLIT -->|분할 가능| CALL[LLM 영어 번역 요청<br/>같은 원문·설정의 과거 실패 사유도 전달]
    SPLIT -->|분할 불가| FAIL[접수 실패 기록]
    SIZE -->|예| CALL
    CALL --> CHECK{셀별 검사 통과?}
    CHECK -->|예| HOLD[통과한 셀 유지]
    CHECK -->|내용·JSON 검사 실패| LIMIT{이 셀의 보완이 3회 미만인가?}
    LIMIT -->|예| REPAIR[최신 오류·회차·보완 지침 추가<br/>숫자·단위·코드 보호 후 실패 셀만 요청]
    REPAIR --> CHECK
    LIMIT -->|아니요| FAIL
    HOLD --> ALL{접수의 모든 대상 셀이 통과했는가?}
    ALL -->|다른 셀 처리 중| CHECK
    ALL -->|모두 통과| WRITE[접수 번역을 DB에 저장<br/>실패 기록 삭제]
    SAVE --> NEXT
    WRITE --> NEXT
    FAIL --> NEXT
    NEXT --> FINISH[선택한 접수 처리 후 영어 색인 갱신]
    CALL -. 시간 초과 .-> TIMEOUT[현재 묶음 종료 후 동시 처리 수 절반<br/>해당 접수 1회 재시도]
    REPAIR -. 시간 초과 .-> TIMEOUT
    TIMEOUT -->|첫 재시도| CALL
    TIMEOUT -->|또 시간 초과| FAIL
```

실패한 셀을 보완하는 동안 이미 통과한 셀은 다시 번역하지 않습니다. 세 번 모두 실패하면 다른 접수 처리는 계속하되, 해당 접수의 일부 번역을 전체 성공으로 저장하지 않습니다. 시간 초과 재시도는 내용 검사 보완 횟수와 별도입니다. 인증·설정 등 보완할 수 없는 오류는 실패로 표시합니다.

영어 대상 열은 제목, 재발방지대책, 문제현상, 발생원인, 현상, 원인(1), 조치내용(1), 원인(2), 조치내용(2)입니다. 빈 셀과 숫자만 있는 셀은 제외합니다.

## 4. 질문부터 답변까지

```mermaid
flowchart TD
    A[한국어 질문·검색 방식·참고 사례 수 선택] --> QUEUE[브라우저별 질문 접수 · 순차 처리]
    QUEUE --> B[DB 원문과 검색 색인 버전 확인<br/>Excel 파일은 다시 읽지 않음]
    B --> C{지원하는 건수 집계 질문?}
    C -->|예| D[DB 직접 집계·결과 표시]
    C -->|아니요| E{접수번호·코드·날짜 조건?}
    E -->|예| EXACT[정확 조건으로 키워드 조회]
    E -->|아니요| MODE{검색 방식}
    MODE -->|키워드| KO[한국어 키워드 검색]
    MODE -->|결합| KO
    MODE -->|벡터 또는 결합| EMB[질문 임베딩·유사 벡터 검색]
    MODE -. 영어 병용을 켠 경우 .-> EN[질문 전체를 영어로 한 번 번역<br/>영어 색인이 있으면 후보 순위 결합]
    KO --> RANK[선택한 방식의 최종 후보 결정]
    EN --> RANK
    EMB --> RANK
    EXACT --> RANK
    RANK --> COMPARE{검색 비교만 요청했는가?}
    COMPARE -->|예| TABLE[후보·순위·시간 표시, 답변 LLM 생략]
    COMPARE -->|아니요| FOUND{후보가 있는가?}
    FOUND -->|아니요| NO[관련 기록 없음 안내]
    FOUND -->|예| CONTEXT[참고 사례 수와 문맥 한도에 맞춰 선택<br/>원문 셀·근거 ID 구성]
    CONTEXT --> CALL[한국어 질문·검증된 영어 질문·원문으로<br/>LLM 한국어 답변 생성]
    CALL --> VALID{근거·인용·숫자·응답 형식 검사}
    VALID -->|통과| OK[답변 본문 표시<br/>인용 번호에서 원문·조치 결과 펼치기]
    VALID -->|유효한 근거 부족 응답| LACK[근거 부족 안내]
    VALID -->|보정 가능한 오류 또는 잘림| LIMIT{이미 재요청했는가?}
    LIMIT -->|아니요| RETRY[같은 근거로 보완 요청]
    RETRY --> CALL
    LIMIT -->|예| ERROR[검사 실패 표시·진단 저장]
```

- 결합 검색은 키워드와 벡터 후보의 순위를 합칩니다. 참고 사례 수는 기본 3건이며 UI에서 1~100건 또는 자동을 선택합니다. 자동은 설정된 문맥과 서버에서 확인할 수 있는 한도, 입력 예약량을 고려합니다. 명시적인 접수번호·코드·날짜는 정확 조회를 우선합니다.
- 질문 번역은 검색과 답변에 재사용하며 원문 질문이 우선입니다. 영어 질문이 검사에 실패하면 한국어만 사용합니다. 벡터 질의에는 원문 질문을 사용하며, 영어 문서가 없어도 검증된 질문 번역은 답변 이해를 도울 수 있습니다.
- 결합 검색에서 벡터를 사용할 수 없으면 키워드 검색으로 돌아가지만, 벡터 전용 모드에서는 오류로 안내합니다. 검색 비교만 요청하면 답변 LLM을 호출하지 않습니다.
- 답변과 인용의 사실 근거는 원문입니다. 채택문과 영어 번역은 검색을 돕는 자료입니다.
- 기본 CS 답변 경로는 최초 요청과 재요청을 합쳐 최대 2회입니다. 통신·입력 오류 등은 별도로 안내합니다.

```mermaid
flowchart LR

같은 날 추가 검사에서는 기존 태그 가점을 2%로 줄이고, 질문–사례 관련성 점수의 가점·직접 정렬을 비교했습니다. 별도로 16조건의 한국어·영어·중국어 48문항을 고정해 숫자·부정·발생 조건을 검사했습니다. 다음 경로 역시 운영에 연결하지 않습니다.

    A -. 실행 중에도 중지 가능 .-> STOP
```

재실행 화살표는 처리 흐름으로의 복귀를 뜻합니다. 이미 끝난 단계는 건너뛰며, 채택 검사 실패 접수만 다듬기 캐시를 사용하지 않고 보완 요청합니다. 벡터가 실패해도 영어는 처리하고, 둘 다 준비될 때까지 미완료 부분을 반복합니다. 임베딩 모델 미설정 시 벡터를 생략하고 키워드 검색 준비라고 표시합니다. 검사를 완화하거나 실패 제안을 정상 결과로 처리하지 않습니다.

자료 화면은 원문·벡터·영어 건수, 접을 수 있는 등록 영역, 6단계 야간 카드, 개별 실행 영역 순서입니다. 완료 단계 수, 시도 횟수, 재시도 남은 시간과 상세 오류를 표시합니다. 중지 요청은 진행 중인 행·묶음을 저장한 뒤 적용하며 서버 응답 제한까지 지연될 수 있습니다.

실행 전 입력·설정 검증은 유지합니다. 실행 중 인증·요청·DB·색인 오류는 자동 재시도하며, 상태 보고 파일 저장 오류는 경고로 남기고 DB 작업을 계속합니다. 인증·설정·권한 등 외부 원인을 해결하지 않으면 반복해도 완료되지 않을 수 있습니다. 브라우저를 닫아도 프로그램이 켜져 있으면 진행되지만, 프로그램 재시작 후에는 자동 실행 버튼을 다시 누릅니다.

기존 API에서 입력 경로를 명시한 야간 요청은 원문을 DB에 누적 등록한 뒤 DB 전체를 처리합니다. 현재 UI는 등록된 DB를 사용해 파일을 읽지 않습니다. 실제 동작과 검증 범위는 [검증 기록](검증기록-20260922.md)에 구분했습니다.
