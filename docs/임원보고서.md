## 1 보고 요지

여러 사람이 작성한 Excel의 고장·조치 이력을 모아, 문제 현상을 질문하면 관련 과거 사례와 원문 근거를 확인하는 시스템을 구현했습니다. 기존 128열 자료에 누적 28열 자료를 추가하고, 중국어·영어 설명을 한국어로 번역해 검색에 활용하도록 확장했습니다. DB 등록 후에는 Excel 파일 없이도 작업할 수 있습니다.

현재는 기능 검증을 마친 시험 운영 단계입니다. 실제 Windows 환경과 업무 자료로 제한된 시범 운영을 진행하고, 검색에 걸리는 시간과 답변의 근거 적합성을 측정한 뒤 적용 범위를 넓히는 것을 제안합니다. 현장의 최종 조치 판단은 담당자가 수행합니다.

### 본 시스템에서 관련 사례를 고르는 Clef 기능 (2026년 10월 8일)

검색한 후보 중 질문에 더 도움이 되는 사례를 앞에 배치하는 **로컬 Clef 기능을 기존 질문 화면에 연결**했습니다. 설정에서 켜거나 끌 수 있고, 이 Mac에서는 준비된 GPU 서버가 필요할 때 자동 시작됩니다. 원문·검토 결과와 기존 검색 자료를 보존합니다. Clef는 답변을 작성하지 않으며, 기존 답변 모델과 원문·숫자·인용 검사가 그대로 처리합니다. 적용 실패는 표시하고 기존 검색 순서로 계속합니다. 최초의 별도 읽기 전용 시험 화면도 보존했습니다.

```mermaid
flowchart LR
    A[문제 현상으로 과거 사례 검색] --> B[Mac GPU의 Clef로 관련 사례 순서 보완]
    B --> C[기존 AI 답변과 원문 검사]
    C --> D[답변·인용·관계 그래프 확인]
```

초기 CPU 시험의 지연과 답변 문맥 부족을 보완하고 GPU 실행으로 전환했습니다. 가상 10만 건의 검색 결과 중 5개 후보를 실제 GPU에서 재정렬하고, 화면에서 변경된 순서를 확인했습니다. 이번 후보 판단은 모델 적재를 포함해 약 26.6초였으며, 짧은 별도 확인 입력의 GPU 최대 메모리는 약 10.3GB였습니다. 한국어 답변 1건도 실제 생성해 유량 값 3개와 인용을 원문에서 확인했고 검사를 통과했습니다. 두 모델을 순서대로 사용해 메모리 부담을 줄이며, 잘린 원문과 불완전한 답변은 채택하지 않습니다. 한국어 업무 정확도 개선·Clef 27B·Windows 현장 성능은 아직 확인하지 않았습니다. 사용자 요청으로 이 Mac의 본 화면에서 활성화했으며, 새 배포본에서는 준비되지 않은 Clef를 자동으로 켜지 않습니다. 본 화면에서 설정 저장과 GPU 서버 자동 시작, 가상 10만 건의 결합 검색 후보 판단을 확인했습니다. 설정된 답변 모델만 순서대로 적재·해제해 두 큰 모델의 메모리 중첩을 피합니다. 접수번호 정확 조회·건수 집계·상세가 고정된 이어서 질문은 기존 흐름을 유지합니다. [구성·검증·남은 판단](Clef-테스트-RAG-20261008.md)을 참고하세요.

본 화면에서도 영어 질문 번역 → GPU 후보 판단 → 한국어 답변을 실행했습니다. 가상 10만 건에서 참고 3건을 사용한 실행은 약 108초였고 인용·수치 검사를 통과했습니다. 자동으로 참고 9건을 선택한 실행은 잘못된 근거 번호와 보정 답변의 잘림을 검사에서 거절했습니다. 큰 모델을 순서대로 사용해도 참고 자료가 늘면 답변 지연과 실패가 남아 있습니다. GPU 작업 종료를 확인하지 못하면 답변 모델을 추가 적재하지 않도록 보호합니다.

이번 결과는 기능 연결을 확인한 것이며, 현장 정답률 향상의 증거는 아닙니다. 원문과 수치가 맞더라도 ‘유량이 증가했다’ 같은 해석까지 모두 보장하지 않습니다. 초기 시범에서는 참고 3건으로 사용하고, 독립 업무 사례에서 답변 적합성과 지연을 함께 평가하는 것이 다음 판단입니다.

### 검색된 사례의 연결과 실제 원문 확인 (2026년 10월 8일)

과거 사례가 왜 검색됐는지 확인할 수 있도록 **관계 보기**를 추가했습니다. 답변 아래에서 펼치면 설비·모듈·부품 이름과 연결된 사례를 볼 수 있습니다. 답변에 실제 인용된 사례를 먼저 표시하고 검색 후보와 구분합니다. 같은 CS에 여러 부품 문제가 있더라도 상세와 작업을 따로 표시합니다.

이제 설비코드를 몰라도 문제 현상으로 검색한 뒤 그래프를 볼 수 있습니다. 모든 검색 방식에서 실제 반환된 사례의 원문 이름을 연결하므로 질문에 설비·모듈·부품 이름을 미리 지정할 필요가 없습니다. 빈 이름은 추정하지 않고, 코드가 없는 모듈·부품 기록이나 이름 한 종류만 있는 기록도 표시합니다. 검색 순위와 답변 검사는 유지하며 추가 AI 호출·관계 테이블을 만들지 않습니다. 가상 10만 건에서 ‘냉각수 저유량 알람이 발생했을 때 과거 조치와 결과는?’의 키워드 상위 3개 사례에 원문 연결 6개가 만들어지는 것을 읽기 전용으로 확인했습니다.

같은 설비·모듈 이름은 화면에 한 번만 표시하고 여러 상세로 연결합니다. 사례를 선택하면 해당 연결선을 강조하므로 반복되는 이름을 읽는 부담을 줄입니다. 원문 기록을 합치는 기능은 아닙니다. 별도 가상 자료 4행과 확인 질문 `세정장비 회전모듈 진동 과거 조치`를 제공하며, 같은 CS의 구동벨트·회전척 기록이 분리되어 있는지 확인할 수 있습니다.

별도의 관계 후보 보완에서는 `SIM-ETCH-001`처럼 원문에 등록된 완전한 코드만 허용하고, 측정값·날짜·수량은 보호합니다. 코드로 찾은 후보 안에서만 관련 사례의 순위를 보완하며 다른 설비로 검색 범위를 넓히지 않습니다. 가상 10만 건의 코드 지정 질문으로 후보 보완 경로 12개를 확인한 선행 검사는 유지합니다. 현재 그래프는 이 후보 보완의 적용 여부와 관계없이 실제 반환된 사례의 원문을 표시합니다. 원문·검토·벡터의 재생성은 필요하지 않습니다. 최종 AI 답변의 품질 향상을 측정한 결과는 아닙니다.

```mermaid
flowchart LR
    Q[문제 현상으로 질문 · 코드 입력 불필요] --> A[기존 방식으로 사례 검색 · 반환된 원문 이름 확인]
    A --> B[같은 설비·모듈은 한 번 표시 · 여러 상세에 연결]
    B --> C[사례 선택]
    C --> D[발생일·현상·원인·조치 원문 확인]
```

선택한 사례의 원문과 셀 위치를 DB에서 바로 확인하므로 Excel을 다시 열 필요가 없습니다. 화면은 최대 10개 경로로 제한하며 추가 AI 호출이나 모델 설치가 필요하지 않습니다. 연결은 함께 기록됐다는 뜻이며 원인이나 해결 효과가 입증됐다는 뜻은 아닙니다. 원문이 바뀌거나 조회에 실패하면 사용자가 잘못된 근거를 읽지 않도록 안내합니다.

Mac 브라우저에서 가상 응답으로 상세·작업 분리, 실제 인용과 후보 구분, 오류 후 재시도, 원문 변경, 빠른 연속 선택, 날짜·빈 셀, 키보드와 모바일 화면을 확인했습니다. 전체 오프라인 회귀 검사도 통과했습니다. 실제 Windows와 업무 자료의 검증 및 사용자가 근거를 더 빨리 찾는지의 측정은 남아 있습니다. 시각화 자체를 검색 정확도 개선의 증거로 보지 않습니다.

### 설비와 부품의 연결로 놓친 사례 보완 (2026년 10월 7일)

설비명과 부품명이 비슷한 기록 속에 섞여 있으면, 뜻이 비슷하다는 이유만으로 다른 설비의 사례가 먼저 나올 수 있습니다. 이를 줄이기 위해 **원문에 같은 상세로 기록된 설비·모듈·부품을 연결해 후보를 보완하는 기능**을 선택 방식으로 추가했습니다. 예를 들어 ‘세정장비의 회전척 진동’을 질문하면 두 이름이 함께 적힌 상세를 추가로 확인합니다. 기존 DB와 검색·답변 검사를 사용하며 새 그래프 서버나 관계 추출용 AI를 설치할 필요는 없습니다.

```mermaid
flowchart LR
    Q[설비·부품을 포함한 문제 질문] --> S[기존 유사 사례 검색]
    Q --> R[원문에 함께 적힌 설비·부품 연결 확인]
    S --> C[관련 후보 보완]
    R --> C
    C --> A[AI 답변과 실제 원문 셀 검사]
```

별도 가상 자료 2,000상세에서 한국어 질문 41개를 비교했습니다. 정답이 있는 34개 질문에서 첫 사례가 정답인 경우는 기존 32개에서 관계 보완 34개로 늘었습니다. 숫자·부정·정상 조건 등 보완 대상이 아닌 질문은 기존 후보를 유지했습니다. 원문과 검토 내용은 전후 같았고 처리 오류·누락은 없었습니다.

이번 결과는 규칙적인 합성 자료의 소규모 개발 검증입니다. 없는 설비·부품을 물은 질문 2개는 두 방식 모두 비슷한 기록을 반환했으며, 관계만으로 근거 부족이나 조치 성공을 판정하지 않습니다. 실제 업무 질문·최종 답변 정확도·Windows 성능은 아직 확인하지 않았습니다. 기본 검색은 유지하고 웹의 **관계 보완 (실험)**을 선택한 경우에만 사용합니다. [평가 보고서](관계검색-비교-20261007.md)에 검증 범위와 제한을 기록했습니다.

### 비슷한 사례를 찾는 모델 교체 (2026년 10월 7일)

문제 현상과 과거 기록의 뜻을 비교하는 검색 모델을 Google의 **EmbeddingGemma 2**로 교체했습니다. 기존 시스템의 DB·키워드 검색·답변 AI를 재사용하고, 모델에 맞춘 새로운 검색 자료를 별도로 만들었습니다. 원문과 담당자의 검토는 유지하며, 이전 Qwen 검색 자료도 보관해 설정을 복원할 수 있게 했습니다.

```mermaid
flowchart LR
    D[보존한 원문과 채택 문장] --> E[새 검색 모델로 자료 준비]
    Q[사용자의 문제 현상] --> E
    E --> S[뜻이 비슷한 과거 사례 검색]
    S --> A[기존 답변 AI와 원문 근거 검사]
    A --> U[한국어 답변과 인용 표시]
```

Mac의 LM Studio에서 실제 모델을 실행했습니다. 한국어·중국어·영어로 만든 8개 기록을 8개 질문으로 찾는 작은 시험에서는 모두 기대한 기록을 첫 번째로 찾았습니다. 이는 연결·검색이 동작하는지 확인한 결과이며, 실제 현장 정확도나 이전 모델보다 우수하다는 증거는 아닙니다. Windows 실기기 동작과 실제 업무 사례 비교는 아직 확인하지 않았습니다. 기존 최소 유사도 설정도 유지했으므로 업무 자료에서 적절한지 확인해야 합니다. 모델의 다국어 지원과 사양은 [Google 공식 모델 카드](https://huggingface.co/google/embeddinggemma-2), 설치·복원은 [사용 안내](../README.md#기존-qwen-설정에서-전환하기)를 기준으로 합니다.

10만 건의 가상 기록 전체에 대해 새 검색 자료를 만들었습니다. 같은 내용은 한 번만 처리해 고유 벡터 14,542개를 생성했고 실패는 없었습니다. 이전 Qwen 검색 자료를 보존했으며 원문·제안·검토의 저장 내용도 전후 같았습니다. 프로그램 재시작 후에도 준비 완료와 10만 건 검색 가능 상태를 확인했습니다. 전체 오프라인 검사와 Windows 배포 파일을 별도 폴더에 풀어 수행한 검사도 Mac에서 통과했습니다. 이 결과는 서비스 연결과 자료 보존의 검증으로, 가상 기록 10만 건의 정답률을 측정한 결과는 아닙니다.

### 모델 교체 후 검색 품질 확인 (2026년 10월 7일)

**새 모델로 바꾸면 업무 검색이 더 좋아진다는 결론은 확인하지 못했습니다.** 같은 10만 건 가상 기록에서 이전에 정한 질문 50개를 다시 검색했습니다. 정답이 있는 질문은 44개이며, 모든 가상 기록이나 실제 업무 질문을 평가한 것은 아닙니다.

새 모델은 짧은 다국어 조건 비교에서 나았지만, 실제 서비스의 결합 검색에서는 정상인 조건과 문제 조건을 혼동한 사례가 늘었습니다. 예를 들어 ‘유량은 정상이고 냉각수 온도만 높음’을 ‘냉각수 저유량’으로, ‘전원을 끌 때만 로봇 팔이 내려감’을 ‘로봇 원점 오류’로 찾았습니다. 높은 유사도 점수만으로 정확한 숫자나 확정된 원인이라고 판단할 수 없습니다.

```mermaid
flowchart LR
    A[같은 가상 기록·고정 질문] --> B[기존 모델과 새 모델로 각각 검색]
    B --> C[정답 사례·누락·잘못된 후보 비교]
```

검색 결과 250개와 조건 결과 96개를 끝까지 검증했고 원문 DB와 설정 파일은 바뀌지 않았습니다. 현재 업무 유형의 품질을 우선한다면 기존 Qwen이 더 유리한 결과입니다. 다만 반복 사용한 합성 자료이므로 모델을 자동으로 되돌리거나 점수 기준을 조정하지 않았습니다. 다음에는 담당자가 정답을 확인한 새 현장 질문으로 후보 누락과 잘못된 조치 안내 여부를 평가해야 합니다. Windows 실기기와 최종 답변 품질은 이번에 검증하지 않았습니다. [상세 보고서](임베딩-품질비교-20261007.md)에 오류 사례·시간·검증 근거를 기록했습니다.

### 과거 사례를 더 좋은 순서로 보여주는 AI 비교 (2026년 10월 1일)

기존 검색이 찾아낸 최대 20개 사례를 추가 AI가 다시 읽고, 질문의 현상과 조건이 잘 맞는 사례를 앞에 놓는 방법을 비교했습니다. 답변을 쓰거나 고장을 확정하는 기능은 아닙니다. 10만 건 가상 자료에서 저장한 후보와 별도 언어·조건 질문을 사용해 두 AI를 각각 98문항으로 실행했고, 실행 실패·누락 없이 결과를 끝까지 검증했습니다.

| 확인 항목 | 기존 순위 | BGE | Qwen |
|---|---:|---:|---:|
| 기존 질문에서 첫 사례가 정답인 경우 | 40/44 | 42/44 | 44/44 |
| 상위 5개 안에 정답이 있는 경우 | 44/44 | 42/44 | 44/44 |

| 최대 20개 사례의 추가 검토 시간 평균 | 추가 검토 없음 | 0.33초 | 1.12초 |

**후속 검증에는 Qwen이 적합합니다.** BGE는 더 빠르지만 이미 찾은 정답 2건을 상위 5개 밖으로 밀었습니다. Qwen도 한국어의 부정 표현과 숫자가 다른 사례를 잘못 판단했습니다. 따라서 AI 점수만으로 답변을 허용하거나 원문 검사를 없애지 않습니다. 이번에는 운영을 바꾸지 않았습니다.

```mermaid
flowchart LR
    A[기존 검색이 찾은 과거 사례] --> B[추가 AI가 질문과 사례 조건 비교]
    B --> C[관련 사례를 앞에 배치]
    C --> D[정답 누락·순위 개선·추가 시간 검증]
    D --> E[새 업무 질문에서 검증 후 운영 여부 판단]
```

반복 사용한 합성 질문에서의 결과이며 현장 정확도 100%를 뜻하지 않습니다. 시간은 Mac의 사례 순위 검토 단계만 측정한 것으로, 검색·번역·답변 작성과 모델 준비 시간은 제외했습니다. Windows와 새 업무 자료는 미검증입니다. [상세 보고서](검색-재정렬-비교-20261001.md)에 원문 오류 사례, 흐름도와 재현 조건을 기록했습니다.

### 선택적 영어 답변 근거 검사의 운영 연결 (2026년 10월 1일)

큰 언어 모델(LLM)은 문장 다듬기·번역·답변을 작성합니다. 별도 임베딩 모델은 비슷한 과거 사례를 찾습니다. 이번에 연결한 mDeBERTa는 **작성된 답변이 실제 인용한 원문에서 뒷받침되는지** 추가 판단합니다. 검색하거나 새로운 조치를 작성하는 모델은 아닙니다.

```mermaid
flowchart LR
    A[LLM이 한국어 답변 작성] --> B[프로그램이 원문 인용·숫자 검사]
    B --> C[LLM이 주장·인용 원문을 따로 영어 번역]
    C --> D[mDeBERTa가 근거 지지 여부 판단]
    D --> E{선택한 운영 모드}
    E --> F[결과 기록: 경고를 보며 시범 운영]
    E --> G[답변 차단: 미지지 답변 1회 보정]
    G --> H[계속 미지지하거나 검사 불가면 답변 거절]
```

기본은 기존 검사이며 추가 기능은 꺼져 있습니다. 설치와 모델 준비 후 **결과 기록**으로 업무 사례를 관찰하고, 오류와 지연이 허용 범위인지 확인한 뒤 **답변 차단**을 선택할 수 있습니다. 같은 영어 문장도 모델 점수가 낮아 거절될 수 있으므로 모델 점수를 업무 정확도나 사실의 확률로 해석하면 안 됩니다. 자동 번역과 긴 근거의 입력 한도도 영향을 줍니다. 원문·DB·검토를 변경하거나 한국어·영어 모델을 모두 통과시키도록 만들지는 않았습니다. [운영 연결의 검증 결과와 한계](영어-근거검사-운영화-20261001.md)를 기준으로 적용 범위를 판단합니다.

Mac의 실제 자동 번역으로 창작 사례 36건을 끝까지 처리했습니다. 검사 불가·누락은 0건이며, 잘못된 설명이 통과한 건수는 기존 9건에서 0건으로 줄었습니다. 반면 올바른 설명을 막은 건수는 1건에서 3건으로 늘었습니다. 추가 검사 시간은 평균 16초로, 전체 질문 시간이 아니라 영어 번역과 추가 판단에 드는 시간입니다. **기능 연결은 완료했지만 자동 차단을 기본으로 채택하지 않으며, 먼저 결과 기록으로 시범 운영합니다.** 기존 개발 탐침의 재검증이므로 새로운 현장 자료의 품질 인증은 아닙니다.

Windows의 자동 검증에서도 설치, 기본 기능 검사, 압축 해제한 배포본 검사와 추가 AI의 CPU 계산이 통과했습니다. 실제 업무 자료와 현장 Windows GPT-OSS 120B의 답변 품질·DRM Excel 접근·여러 사용자의 동시 처리 성능은 별도 검증이 필요합니다. 검색 결과의 순서를 추가 AI로 바꾸는 방안은 아직 적용하지 않았으며, 관련 사례를 상위에서 더 잘 찾는지 확인한 뒤 판단합니다.

### 공개 모델로 답변의 뜻과 근거를 비교하는 실험 (2026년 10월 1일)

현재 검사는 숫자와 인용을 확인하지만, 모든 의역의 뜻까지 보증하지는 않습니다. ‘발주했지만 아직 교체하지 않음’을 ‘교체 완료’라고 설명하거나, 같은 접수의 다른 부품 조치를 가져오는 오류를 공개 모델이 추가로 찾을 수 있는지 비교합니다. Grok이 운영과 분리된 실험 코드를 작성하고 Codex가 원문 연결·실행·결과를 검증합니다.

```mermaid
flowchart LR
    A[창작 원문과 올바른·잘못된 답변 고정] --> B[인용한 원문만 AI에 전달]
    B --> C[기존 검사와 두 공개 모델 비교]
    C --> D[언어별 오답 통과와 정답 거절을 함께 확인]
    D --> E[실험 결과로 다음 판단]
```

한국어·혼합 원문은 mDeBERTa로, 직접 작성한 영어 대응문은 같은 mDeBERTa와 MiniCheck로 각각 검사합니다. 같은 AI에서 언어를 바꾼 효과와 같은 영어에서 AI를 바꾼 효과를 비교합니다. 실제 Excel과 운영 DB는 사용하지 않습니다. 영어 결과는 번역 품질을 입증하지 않으며, 창작 사례의 판정이 실제 업무 정확도를 대표하지 않습니다. [조건·결과와 미확인 사항](공개모델-근거검사-실험-20261001.md)을 따로 기록하고 운영 적용 여부를 구분합니다.

올바른 설명 17건과 근거가 부족하거나 잘못된 설명 19건을 비교했습니다. 기존 검사만으로 통과한 잘못된 설명 9건은 세 모델 경로를 각각 결합하면 모두 0건으로 줄었습니다. 올바른 설명을 막은 건수는 기존 1건, 한국어 mDeBERTa 결합 2건, 영어 mDeBERTa 결합 1건, 영어 MiniCheck 결합 4건입니다. 이 창작 표본에서는 영어 mDeBERTa가 정상 답변을 가장 적게 막았습니다. **이 사전 작성 영어 결과만으로 자동 차단의 운영 채택을 결정하지 않습니다.** 영어 모델도 조치의 효과와 음수 부호를 잘못 판단해 기존 원문 검사를 유지해야 합니다.

Mac의 CPU에서 세 모델 경로 각각 실제 35쌍을 계산했고 빈 인용 1건은 모델에 보내기 전에 막았습니다. 기존 규칙을 포함한 네 경로 36건씩을 완료했으며 실행 오류와 누락은 없었습니다. 144건의 원문 연결·판정과 지표를 다시 대조했고 관련 검사 25개를 통과했습니다. 같은 AI의 두 언어 판정은 2건에서 달랐으며 별도로 기록합니다. 이전 결과·검증은 보존했습니다. 이 절은 사전 작성 영어 비교이며 위의 실제 자동 번역 운영 연결과 구분합니다. 현장 자료와 Windows 120B 모델의 검증을 마친 결과는 아닙니다. 다음 판단은 새 업무 사례에서 검토 대상으로 표시하는 방식부터 검증하는 것입니다.

### 기록의 뜻을 바꾸는 번역을 줄이는 개선 (2026년 9월 30일)

“배선 접촉 불량을 확인했다”라는 이력이 “접촉 불량을 확인하라”라는 지시로 번역되거나, “재발 여부 미확인”이 “재발 없음”으로 읽히는 사례를 확인했습니다. 한국어 정리와 영어 번역에서 알려진 상태 변경이 발견되면 오류 이유와 함께 다시 요청합니다. 영어 지시문에는 구체적인 예시를 유지하며 영어 칸에 한국어·중국어 문장이 그대로 남는 경우도 재요청합니다.

잘못된 영어는 검색 색인과 재사용에서 제외하며 원문·검토는 유지합니다. 숫자에 붙은 원래 단위는 보존합니다. 모든 문장의 의미를 판정하는 기능은 아니므로 복잡한 표현과 현장 고유명사는 원문 확인이 필요합니다. 기존 통합 생성은 실험으로 유지하고 운영 기본 흐름은 변경하지 않습니다. [검증 보고서와 흐름도](번역-의미보존-개선-20260930.md)에 확인한 범위와 미확인 사항을 기록합니다.

```mermaid
flowchart LR
```

### 한국어 정리와 영어 번역을 함께 요청하는 비교 (2026년 9월 30일)

Mac의 가상 100행 비교에서 통합 요청은 모델 호출 240→170회, 처리 시간 합계 772.6→648.0초, 서버 보고 토큰 208,571→136,794로 줄었습니다. 원문·코드 해시와 200개 체크포인트를 대조하고 오프라인·배포 검사를 통과했습니다. 형식·수치 검사를 통과해도 영어 칸에 한국어가 남거나 확인 사실이 지시로 바뀌는 사례가 있어 운영 기본값은 유지합니다. 실제 업무의 의미 정확도와 Windows 120B 성능은 별도 확인이 필요합니다.

AI에 같은 내용을 반복해서 보내는 횟수를 줄일 수 있는지 확인하기 위해, 한국어 정리와 검색용 영어 번역을 한 번에 받는 실험을 추가했습니다. 원문을 보존하고 두 결과를 따로 검사합니다. 번역만 실패하면 한국어 성공분을 유지하고 번역만 재요청합니다. 한국어를 보정하거나 사람이 수정하면 그 최종 문장을 기준으로 영어를 다시 만듭니다.

```mermaid
flowchart LR
    A[원문 보존] --> B[한국어 정리·영어 후보 함께 생성]
    B --> C[각 결과를 따로 검사]
    C --> D[한국어 성공분 유지]
    D --> E[같은 한국어의 정상 영어만 재사용]
```

작성자마다 표현이 다른 Excel에서는 같은 증상을 다른 말로 기록하기 쉽습니다. 과거 조치를 찾더라도 실제로 해결됐는지, 재발했는지, 아직 시행하지 않은 조치인지 원문을 다시 확인해야 합니다. 이 시스템은 기록을 찾고 비교하는 일을 돕고, 답변에서 해당 원문까지 바로 확인하도록 구성했습니다.

| 현재 가능한 기능 | 업무에서 달라지는 점 |
| --- | --- |
| 여러 Excel을 순차 누적 등록 | 파일을 한 번에 대기시키고 오류 파일을 제외해 계속 처리합니다. |
| 다국어 번역과 검토 결과 저장 | 중국어·영어 설명도 한국어로 정리하고 원문과 비교합니다. |
| 단어 검색과 의미 검색을 결합 | 표현이 달라도 관련 증상의 과거 사례를 찾을 수 있도록 돕습니다. |
| 한국어 답변과 원문 근거 제공 | 조치 내용과 결과를 원문에서 확인하고 판단합니다. |
| 야간 자동 처리와 실패분 재시도 | 성공할 때까지 재시도하며 단계·남은 대기 시간을 표시합니다. |

기대 효과는 자료 탐색과 정리에 드는 수작업을 줄이는 것입니다. 시간 절감률, 비용 절감액, 실제 업무 질문의 정답률은 아직 측정하지 않았습니다.

## 2 시스템이 동작하는 과정

RAG는 **질문과 관련된 기록을 먼저 찾고, 찾은 기록을 근거로 AI가 답하는 방식**입니다. 현재 시스템은 회사 자료로 AI 모델을 새로 학습시키지 않습니다.

![자료 준비와 검색의 기본 구조 · 추가 영어 근거 검사는 위 흐름도 참조](assets/cs-rag-flow.png)

자료를 처음 등록할 때 원문 셀의 내용과 자료형, 파일명, 시트명, 셀 주소를 보관합니다. 문장 다듬기는 별도의 수정 제안을 만들며, 검토해 채택한 내용이 검색에 반영됩니다. 원문 자체를 AI 문장으로 덮어쓰지 않습니다. 원문 등록만으로 단어 검색을 시작할 수도 있습니다.

의미 검색은 문장을 의미 비교용 숫자 목록인 ‘벡터’로 바꾸어 비슷한 사례를 찾습니다. 누적 자료는 채택한 한국어 번역도 벡터에 반영합니다. 영어 번역은 선택적인 검색·질문 이해 보조 자료이며, 영어 번역문을 별도로 벡터화하지는 않습니다. 인용 근거는 번역 전 원문입니다.

질문할 때에는 DB에 저장된 사례를 검색하고, AI가 관련 원문을 참고해 답변합니다. 인용과 숫자 등을 검사한 뒤 답변과 근거를 구분해 보여 줍니다. 선택한 경우에만 영어 mDeBERTa로 추가 검사합니다. 근거가 부족하면 그 상태를 알리며, 단순 건수 질문은 지원하는 조건에 한해 DB에서 직접 계산합니다.

## 3 자료를 누적하고 보호하는 방식

최대 100파일을 한 번에 대기시켜 순서대로 등록합니다. 오류가 생기면 해당 파일 전체를 제외하고 다음 파일을 계속 처리합니다. 앞선 성공분은 보존하며, 문제를 수정한 뒤 실패 파일만 재시도할 수 있습니다. 브라우저를 닫아도 계속되지만 프로그램 재시작 시 대기 목록은 초기화됩니다. Excel 수식은 계산 완료 값을 읽으며, 입력 오류는 파일과 셀 위치·수정 방법을 알려줍니다.

새 접수번호는 추가하고, 번호와 원문이 같으면 기존 처리 결과를 재사용합니다. 번호가 다르면 내용이 같아도 별도 사례입니다. 두 양식의 같은 CS 번호는 원문을 각각 보관하고 함께 조회하며 접수 건수에서는 한 건으로 셉니다. 누적 자료의 다른 내용은 새 상세로 추가합니다. CSList는 같은 파일의 수정분을 갱신하고, 다른 파일에서 같은 번호의 내용이 다르면 해당 파일 등록을 중단합니다.

등록이 완료되면 문장 다듬기, 검토, 번역, 벡터 생성과 질문은 저장된 DB를 사용합니다. Excel을 수정해도 다시 등록하기 전에는 DB에 반영되지 않습니다. 원본 파일을 삭제하려면 등록 건수와 원문을 먼저 확인하고, 프로그램을 종료한 상태에서 설정 파일과 출력 폴더 전체를 백업해야 합니다.

야간 실행은 검사 통과 제안을 자동 채택하고 벡터·영어 자료를 준비합니다. 모든 단계의 실패를 성공 또는 사용자 중지까지 재시도하며 성공분은 재사용합니다. 화면에서 6단계와 재시도 대기를 확인합니다. 인증·설정 등 외부 원인이 남으면 완료되지 않을 수 있습니다.

### 9월 26일 구조 개선: 검토 저장 시 불필요한 전체 재처리 제거

과거에는 한 접수의 검토를 저장해도 전체 접수의 검색 자료를 다시 만들었습니다. 이를 검토한 접수만 갱신하도록 개선했습니다. 개별 검토·일괄 채택·야간 실행이 같은 저장 절차를 사용하며, 원문을 두 번 읽는 작업과 중복된 설치 목록도 정리했습니다. 사용자가 새 설정을 입력하거나 자료를 다시 등록할 필요는 없습니다.

```mermaid
flowchart LR
    A[검토 결과 입력] --> B[해당 접수 원문과 대조]
    B --> C[해당 접수만 저장·검색 자료 갱신]
    C -->|완료| D[필요한 벡터·영어 번역 갱신]
    C -->|저장 오류| E[기존 검토·검색 자료로 함께 복구]
```

원문·셀 위치·기존 검토 결과는 보존합니다. 오래된 검색 자료는 필요한 경우에만 한 번 이관하며, 깨진 제안이 있으면 실패를 알리고 정상 제안의 일괄 처리를 계속합니다. 이 변경은 저장·검색 자료 준비 과정의 개선이며 모델의 판단 품질을 높였다는 뜻은 아닙니다.

Mac에서 가상 2,000건을 같은 조건으로 세 번씩 실행한 결과입니다. 한 건을 저장할 때는 해당 접수만 갱신하고, 모든 접수를 일괄 채택할 때는 기존 전체 갱신을 사용해 대량 처리 성능도 유지했습니다.

| 처리 구간 | 변경 전 중앙값 | 변경 후 중앙값 |
| --- | ---: | ---: |
| 2,000건 원문 DB 등록·검색 자료 생성 | 1.827초 | 1.584초 |
| 접수 한 건의 검토 저장 | 3.104초 | 0.006초 |
| 전체 미검토 제안 일괄 채택 | 11.184초 | 10.187초 |

공개 가상 샘플 8건을 접수번호를 달리해 2,000건으로 만들었으며, 메모리 SQLite와 모의 번역·임베딩을 사용했습니다. 원문 등록 시간에는 Excel 읽기를 포함하지 않고, 검토 저장 시간에는 후속 모델 호출을 포함하지 않습니다. 변경 전후에 11개 질문을 세 가지 검색 방식으로, 검토 전·개별 검토 후·일괄 채택 후에 비교했습니다. 이를 세 번 반복한 **297개 비교에서 검색 순위와 원문 근거가 같았고**, 원문·제안·검토 값·검색 자료·벡터의 논리적 저장 내용도 같았습니다. 검토 시각과 색인 내부 저장 구조는 동일성 비교에서 제외했습니다.

이는 Mac의 제한된 자동 시험 결과입니다. 실제 Windows의 디스크 DB·DRM Excel 처리 시간, 10만 건의 처리 성능과 실제 AI 답변 품질은 이번 구조 개선 시험의 검증 범위에 포함하지 않았습니다.

전체 오프라인 검사 39개 PASS 항목과 새 Windows 배포본 71개 파일의 독립 압축 해제·오프라인 실행 검사를 통과했습니다. 저장 실패 시 원문·검토·검색·벡터 자료의 동시 복구, 구형 색인 이관의 롤백, 전체 보고서의 접수 누락 방지를 포함합니다. 재확인 명령은 프로젝트 루트의 `.venv/bin/python windows-demo/test_demo.py`와 `.venv/bin/python package_windows.py`입니다. 배포본 실행 검사는 Mac에서 수행했으며 Windows 실기기 시험과 구별합니다.

### 9월 26일 추가 검토: 증상 자동 분류로 검색을 개선할 수 있는가

작은 다국어 분류 모델인 GLiNER로 질문과 과거 사례의 증상을 분류하고, 같은 분류의 사례를 조금 더 앞에 표시하는 방법을 시험했습니다. 기존 합성 질문 50개와 고정된 검색 후보를 사용해 실제 로컬 모델로 비교했습니다.

상위 5건의 평균 적합성은 72.0%에서 72.4%로 소폭 높아졌지만, 정답이 있는 44개 질문에서 첫 번째 사례가 맞는 경우는 40개에서 38개로 줄었습니다. 추가 시간은 평균 약 1초였습니다. 전기 이상·압력 이상처럼 넓은 분류가 같더라도 실제 고장 조건이 다른 사례를 앞에 놓은 문제가 있었습니다.

**이 방식은 운영에 적용하지 않습니다.** 기존 검색, DB와 사용자 화면은 유지합니다. 실제 업무 자료의 개선을 입증한 결과도 아닙니다. 다음 비교에서는 별도로 정답을 확인한 현업 질문과 발생 조건을 구분하는 검색 모델이 필요합니다. [상세 실험 보고서](GLiNER-실험-20260926.md)에 결과와 재현 절차를 기록했습니다.

추가로 가점을 줄이는 방법과 질문·사례의 관련성을 직접 판단하는 방법을 비교했습니다. 직접 정렬은 관련 사례의 평균 비율을 높였지만, 기존에 상위 3건에서 정답을 찾던 44개 질문 중 5개에서 정답을 놓쳤습니다. 새 합성 조건을 한국어·영어·중국어로 표현한 48문항에서는 숫자 자릿수와 부정 조건을 잘못 판단하는 경우도 확인했습니다. 따라서 운영 미적용을 유지하며, 평균 지표 하나만으로 개선을 판단하지 않습니다. [추가 실험과 흐름도](GLiNER-추가실험-20260926.md)에 자세한 결과를 기록했습니다.

질문과 사례를 영어로 번역한 뒤 비교하는 검사도 완료했습니다. 기존 검색 순위를 조금만 조정하는 방식은 정답이 있는 44개 질문에서 첫 결과 적중을 40개에서 41개로 높였고, 상위 3건에 정답을 포함하는 44개 결과는 유지했습니다. 반면 순위를 전부 바꾸면 정답 2개를 상위 3건에서 놓쳤습니다. 별도 다국어 조건에서는 한국어 질문의 결과가 좋아졌지만 전체 언어의 개선은 일관되지 않았습니다.

**영어 번역이 모든 문제를 해결하지는 않습니다.** 숫자가 다른 사례를 같은 현상으로 보는 오류와 배기·벤트를 혼동한 번역이 남았습니다. 따라서 운영 검색은 유지하고, 용어 번역을 안정화한 뒤 새 업무 질문에서 작은 순위 조정 방식을 검증하는 것이 다음 판단입니다. 이번에는 번역 준비에 약 7.3분의 배치 처리 시간이 들었고, 저장된 번역으로 최대 20개 후보를 분류하는 단계는 평균 약 1.45초였습니다. 실제 사용자 응답 시간이나 현업 정확도 수치는 아닙니다. [영어 번역 비교 보고서](GLiNER-영어번역-실험-20260926.md)에 결과·한계·흐름도를 함께 기록했습니다.

### 9월 26일 추가 검토: Mac GPU에서 새로운 검색 판단 모델 실행

LEV라는 작은 언어 모델로 질문과 과거 사례의 조건이 맞는지를 판단하는 방법도 별도 비교했습니다. 앞선 실험의 영어 번역과 검색 후보를 재사용해 번역 변경 효과와 모델 변경 효과를 구분했습니다. 같은 입력은 한 번만 계산하고 각 문항의 결과를 저장하도록 구성했습니다.

이번 작은 시험에서는 자료를 찾은 뒤 설명하는 단계에 보완점이 남았습니다. 조치 셀만 인용하면서 다른 열의 현상을 설명하거나, 조치는 적고 결과를 생략하거나, 답할 근거가 있는데도 보류한 경우가 있었습니다. 다음에는 필요한 인용 열과 조치 결과를 빠뜨리지 않도록 개선하고 검증해야 합니다. 모델 교체는 이번 결과만으로 결정하지 않습니다. 이는 Mac의 가상 자료와 Codex 검토 결과이며 실제 업무 정확도·Windows 120B 성능을 뜻하지 않습니다.

### 9월 28일 보완: 숫자 검사 안내와 날짜 오판 수정

사용자가 숫자·부호 검사 실패를 보고해, 어느 답변의 어떤 숫자가 어느 인용 열과 맞지 않는지 표시하도록 보완했습니다. 동일한 비교 정보를 AI의 자동 수정 요청에도 보냅니다. 예를 들어 원문은 30분인데 답변이 90분이면 두 값을 나란히 안내합니다. 숫자가 다른 열에 있다면 그 열을 인용해야 하며, 원문에 없는 값은 통과시키지 않습니다. 숫자의 쉼표·소수 표기를 유지하고 목록 번호를 추가하지 않도록 요청도 명확히 했습니다.

사용자가 알려 준 질문은 스핀 문제의 조치, 참고 날짜, 중복 없는 인용을 함께 요구했습니다. 같은 조건의 가상 사례에서 날짜가 `2026-09-01`에서 `2026.09.01`로 표현되면 잘못 거절하는 문제를 재현해 수정했습니다. 같은 년월일의 표기 차이는 허용하되 다른 날짜는 계속 차단합니다. 인용 중복을 줄이면서 날짜 근거까지 빠뜨리지 않도록 요청도 보완했습니다.

위 48답변 평가는 이 보완 이전 결과입니다. 사용자가 보고한 다른 PC의 실패 응답·원문은 확보하지 못해 해당 건의 해결 여부와 실제 재보정 성공률은 확인되지 않았습니다. 모의 응답과 HTTP 검사에서는 잘못된 숫자의 차단, 근거 열 보완 후 통과, 상세 오류 전달을 확인했습니다.

보완 후 Mac의 GPT OSS 20B에 가상 스핀 사례 2건과 날짜·중복 인용 조건을 실제 요청했습니다. 두 사례의 조치와 날짜, 원문 인용을 확인했고 중복 셀 주소는 없었습니다. 한 질문의 동작 확인이며 업무 정확도 개선률을 뜻하지 않습니다. Windows 배포 파일은 Mac에서 압축 해제·오프라인 전체 검사를 통과했으며 실제 Windows·120B·업무 DB는 미검증입니다.

### 9월 28일 추가 비교: AI에 주는 지시의 언어

AI에 주는 작성 지시를 영어로 바꾸면 누락이나 잘못된 해석이 줄어드는지 확인하는 비교를 추가했습니다. 사용자의 질문, 업무 원문과 최종 답변은 계속 한국어로 유지합니다. 저장된 검색 자료가 같은 24개 질문에 날짜·숫자 경계 질문 4개를 더해, 한국어 지시와 영어 지시로 각각 답하게 합니다. 검색 결과가 달라져 생기는 효과와 구분하기 위한 구성입니다.

총 56개 답변의 실행과 원문 대조를 마쳤습니다. 같은 내용을 지시하는 42개 항목은 영어로 작성했을 때 분량이 약 18% 줄었지만, 추가 보정이 늘어 전체 입력 절감은 작았습니다.

| 비교 결과 | 한국어 지시 | 영어 지시 |
| --- | ---: | ---: |
| 필요한 내용·인용 대조 통과 — 적절한 보류 포함 | 15/28 | 16/28 |
| 답변이 있었으나 보완 필요 | 12 | 7 |
| 최종 답변 생성·검사 실패 | 1 | 5 |
| 평균 처리 시간 | 42.20초 | 59.34초 |

영어 지시가 더 완전한 설명을 만든 사례도 있었지만 최종 실패가 늘어 사전에 정한 채택 조건을 충족하지 못했습니다. **운영 기본값은 한국어로 유지합니다.** 후속 개선은 인용 주소의 오기와 원문 결과·보조 상태의 혼동을 줄이는 데 집중할 필요가 있습니다. 이번 결과는 Mac의 작은 가상 자료를 Codex가 대조한 것이며, 실제 업무 정확도와 Windows 120B 효과는 별도 확인 대상입니다. [비교 보고서와 흐름도](영문-프롬프트-비교-20260928.md)에 문항별 결과와 재현 방법을 기록했습니다.

## 5 시범 운영에서 확인할 사항

LM Studio의 GPT OSS 20B에서 중국어 셀의 한국어 번역을 확인했습니다. 추가 2행 시험은 번역·보정과 벡터 생성을 지났지만 답변이 잘려 전체 흐름은 완료하지 못했습니다. 이는 작은 시험이며 전체 자료의 번역 품질 평가가 아닙니다.

현재 검증으로 Windows의 실제 DRM 연동, GPT OSS 120B의 업무 답변 품질, 동시 사용자 수에 따른 처리 성능까지 확인됐다고 볼 수는 없습니다. 자동 숫자·인용 검사는 원문 대비 일부 오류를 차단하지만 문장 의미와 인과관계 전체를 보증하지 않습니다.

실제 과거 사례와 현업 질문을 정해 기존 Excel 탐색 방식과 비교하는 것이 다음 단계입니다. 아래 항목의 목표치는 시범 운영 전에 담당 부서와 합의하고, 같은 질문으로 비교해야 합니다.

| 측정 항목 | 측정 방법 |
| --- | --- |
| 필요한 사례를 찾는 시간 | 같은 질문으로 기존 방식과 시스템 사용 시간을 비교합니다. |
| 검색 사례의 적합성 | 상위 3개 사례가 질문의 증상·장비·조건에 맞는지 현업 담당자가 판단합니다. |
| 답변 근거의 정확성 | 조치·결과·미실시·재발 등의 설명이 인용 원문과 일치하는지 확인합니다. |
| 운영 안정성 | 실패 건수, 재시도 후 미완료 건수, 응답 대기 시간, 백업 복원 여부를 기록합니다. |

실제 Windows에서 DRM 등록부터 원본 삭제 후 질문까지 확인하고, 업무 자료의 검색·답변 오류를 평가해야 합니다. 확대 적용 전에는 로그인·권한 관리와 정기 백업·복구 절차를 마련해야 합니다. 현재 UI에는 사용자 인증·역할별 권한이 없어 신뢰할 수 있는 내부 사용자 범위로 운영합니다.

원문과 질문의 일부는 설정한 답변·임베딩 서버로 전달됩니다. 사내 자료를 사용할 때는 해당 서버의 위치와 접근 가능 범위를 확인해야 합니다. 여러 브라우저의 질문은 대기열로 순차 처리하며, 동시 접속이 모두 동시 답변을 뜻하지는 않습니다.
